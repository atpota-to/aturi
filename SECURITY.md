# Security Policy

## Reporting a vulnerability

Do not open a public issue.

Report privately through [GitHub Security Advisories](https://github.com/atpota-to/aturi/security/advisories/new), or email [aturi@atpota.to](mailto:aturi@atpota.to).

Include what you can: the affected surface, steps to reproduce, and what an attacker gets out of it. A working proof of concept is welcome but not required to file.

This is a small project with one maintainer. Expect an acknowledgement within a week. If you have not heard back after that, DM [@aturi.to](https://bsky.app/profile/aturi.to) on Bluesky and reference the report without describing the issue publicly.

## Scope

In scope:

- **aturi.to** and its API routes, including `/api/resolve` and the OpenGraph image routes
- **The browser extension** on Chrome, Firefox, and Safari
- **`@aturi.to/waypoints` and `@aturi.to/waypoints-react`** as published on npm

Areas worth a look, since they carry the interesting risk:

- Server-side fetching. Records reference arbitrary URLs and PDS hosts, and the app fetches some of them. `src/utils/ssrfGuard.ts` and `src/utils/upstreamFetch.ts` exist to bound that.
- Record rendering. Record contents are attacker-controlled: anyone can write anything to their own repo and send you a link to it. `src/utils/sanitize.ts` handles this.
- OAuth. Sign-in is atproto OAuth with DPoP-bound tokens held in the browser. There is no Aturi-side account database and no server-side session store, so token handling and scope enforcement are the things to probe.
- Extension permissions. The extension has host permissions and rewrites URLs through `declarativeNetRequest`. Redirect rules that can be induced to send a user somewhere unintended are in scope, as is anything that leaks browsing activity.
- Universal links. `aturi.to/...` URLs are meant to be pasted into untrusted places. Open redirects and preview-based content injection count.

Out of scope:

- Vulnerabilities in third-party Atmosphere clients the catalog links to. Report those to the client's maintainers. If aturi.to is sending users somewhere unsafe, that is in scope.
- Vulnerabilities in upstream atproto infrastructure (PDS implementations, Bluesky's AppView, Constellation, Jetstream). Report upstream.
- Missing hardening headers, TLS configuration ratings, and similar findings with no demonstrated impact.
- Denial of service through traffic volume.
- Reports generated by an automated scanner with no verification. If a tool found it, reproduce it first and say what you observed.

## Testing

Test against your own account and your own records. Do not test against other people's repositories, do not attempt to access data you do not own, and do not run load or fuzzing tools against the hosted site. Running aturi.to locally is straightforward and is the right way to probe most of this; see [CONTRIBUTING.md](CONTRIBUTING.md).

## Disclosure

Coordinated disclosure. Report privately, and publish once a fix has shipped. Credit is given in the advisory unless you would rather stay anonymous.
